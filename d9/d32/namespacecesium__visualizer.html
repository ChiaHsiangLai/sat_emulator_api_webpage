def cesium_visualizer._grant_root_x_access ( )
private 
Ask the X server to accept connections from local root, via the
real desktop user's already-working session -- instead of trying to
hand root a copy of the right auth cookie.

_real_user_xauthority()'s approach (guess where the cookie file lives,
point XAUTHORITY at it) turned out not to be reliable enough on its
own: display managers differ (GDM's /run/user/<uid>/gdm/Xauthority is
only one convention among several), so a guessed path can miss
entirely and this (root, via sudo) process is left with no valid
cookie -- reproducing "Authorization required, but no authorization
protocol specified" even after the guess-the-path fix.

xhost sidesteps the whole problem: it's a *host-based* ACL on the X
server ("also accept local root"), not a cookie-matching problem, so
it doesn't matter which Xauthority convention this desktop uses. The
trick is *who* runs it -- `sudo -u <real user> xhost ...` executes as
that user, who already has a working session (correct HOME/cookie by
construction, since their desktop set it up), so this one call doesn't
hit the same chicken-and-egg problem root calling X directly does.
Best-effort: xhost may be missing, or this may not even be a plain
Xorg/xhost-compatible session -- failure here just means the
XAUTHORITY fallback in _real_user_xauthority() is all that's left,
not a hard error for the whole visualizer.

def cesium_visualizer._real_user_xauthority ( )
private 
Locate the actual logged-in desktop user's X11 auth cookie file.

This whole simulation runs under sudo, which resets $HOME to /root by
default. X11 clients look up their connection auth cookie at
$HOME/.Xauthority unless XAUTHORITY is set explicitly, so a Chrome
launched by this (root) process with no override tries root's own
(nonexistent, or plain wrong) Xauthority -- producing "Authorization
required, but no authorization protocol specified" and a GPU-process
init failure, even though DISPLAY itself is fine. SUDO_USER is the
same mechanism _default_base_dir() already relies on to recover the
real invoking user's identity when running as root.

Checks the GDM/systemd runtime-dir location before the traditional
$HOME/.Xauthority: verified empirically on this exact machine (Ubuntu +
GNOME/GDM, per OBS's own "Desktop Environment: ubuntu:GNOME" log line)
that the active cookie actually lives at /run/user/<uid>/gdm/Xauthority
-- $HOME/.Xauthority either doesn't exist there at all, or (worse,
found the hard way) can belong to a completely different, unrelated
user left over on a shared machine, which would silently hand Chrome
the wrong cookie instead of just failing loudly.
