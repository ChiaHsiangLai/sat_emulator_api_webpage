Detailed Description

web_page_client.py — simulates a browser loading a web page: fetches
index.html, discovers its embedded resources (href/src references), then
fetches all of them over <concurrency> persistent connections — the same
parallel-connection-pool behavior a real browser uses on page load (e.g. 6
concurrent connections, each reused for several sequential requests), rather
than opening a brand new connection per object.

Resources are split round-robin into <concurrency> groups; each group is
fetched via a single curl invocation chained with `--next`, which reuses the
same TCP connection for every URL in that group instead of reconnecting each
time. Groups run concurrently. There is no pacing: a real page load fetches
everything as fast as possible, so the total elapsed time is a genuine
page-load-time measurement.

Each object within a group is individually bounded by --speed-limit /
--speed-time (STALL_SPEED_BYTES_PER_SEC / STALL_WINDOW_S): only a sustained
near-zero-throughput stall gives up on that object, moving on to the next
--next stage (reusing the connection if it's still alive, reconnecting if
not). This is deliberately speed-based rather than a fixed total-time cap —
a large object legitimately needs longer to transfer even when everything is
healthy, and a fixed cap can't tell "big but fine" apart from "actually
stuck" without scaling with WEB_PAGE_SIZE_MB. A large-but-genuinely-
transferring object is therefore allowed to keep going as long as it needs
(up to the whole group's own time budget), while a real stall is still
detected and moved past.

Results stream out in real time as each object finishes, rather than
appearing all at once when a whole group completes. This requires two
things: (1) curl is run under `stdbuf -oL` to force line-buffered stdout —
by default curl fully buffers stdout when it isn't a TTY (as it is here,
piped to Python), so its -w output for completed objects would otherwise sit
in curl's own buffer and only appear once the whole multi-object chain exits;
(2) fetch_group reads that output incrementally (via select() on the pipe)
and reports each line through a callback the moment it arrives, instead of
capturing the whole process's output in one blocking subprocess.run() call.

NOTE: this project previously tried HTTP/1.1 keep-alive against Python's
plain http.server for an earlier HLS video client and hit
ConnectionResetError / BrokenPipeError under this same mininet topology.
web_page_server.py enables keep-alive the same way — if requests here start
failing with connection resets instead of stalls, that's the same known
rough edge resurfacing, not a new bug.

Loads the page (index.html + every discovered resource) over and over —
like a user repeatedly reloading/browsing — until <duration_s> elapses, not
just once. On exit (whether the run_duration budget ran out between page
loads, mid-page-load, or the page never became available), writes a small
key=value summary to <summary_path> with a status/elapsed_s pattern, plus a
page_loads_completed count and object totals accumulated across every page
load in this run.

Usage:
    web_page_client.py <page_url> <duration_s> <summary_path> [<concurrency>]
    e.g. web_page_client.py http://10.0.255.254:5099/index.html 300 \\
         log_file/UE_10.0.200.101/web_page_duration.txt 6

Fetch urls sequentially over a single curl invocation, chained with
--next so the TCP connection is reused across all of them instead of
reconnecting per object. Each object is individually bounded by
--speed-limit/--speed-time (a real stall, sustained near-zero throughput,
gives up on just that object and moves to the next --next stage) rather
than a fixed --max-time, so a large-but-genuinely-transferring object
isn't cut off early just for being big.

Calls on_result(url, elapsed_s_or_None) the moment each object's result
is available (elapsed_s_or_None is None for a failure: non-200 response,
curl error, connect-timeout, or a sustained stall) — in the same order as
urls. Any urls whose result never arrives because the group ran out of
time (timeout_s) or stop_event got set are reported as None too.

def web_page_client.fetch_text (   url) 
GET url via curl and return the response body as text, or "" if curl
failed. Without checking the exit code, a 404 (e.g. before the server
has the page ready yet) still returns a non-empty HTML error body
that would otherwise be misread as valid page content.
