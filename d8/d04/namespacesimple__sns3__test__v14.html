def simple_sns3_test_v14._ensure_obs_screen_scene_collection (   resolution = '640x360')
private 
Write an OBS scene collection whose source is a live X11 desktop
capture (Display Capture / xshm_input) instead of a file — used by
screen_contribute. Unlike a camera, X11 capture isn't an exclusive
resource: verified empirically that two concurrent x11grab captures of
the same display both succeed with identical output, so every UE's OBS
instance can independently capture the same desktop with no
v4l2loopback-style relay needed. Always overwritten, same reasoning as
_ensure_obs_scene_collection.

bounds_type=2 (OBS_BOUNDS_SCALE_INNER) + bounds matching the canvas
resolution scales the whole captured desktop down to fit — without it
(bounds_type=0, no bounds/scaling), a source larger than the canvas
(e.g. a real 1920x1080 desktop into a 640x360 canvas) is mapped 1:1
from the origin, so only its top-left corner is visible instead of the
whole screen (found by testing after a report that the OBS window
wasn't showing the full desktop).

def simple_sns3_test_v14._prepare_test_webpage (   size_mb,
  num_objects 
)
private 
Build (or rebuild) a synthetic web page under DATA_DIR/test_webpage/,
for UE_TRAFFIC_TYPE=webpage.

Generates index.html referencing num_objects embedded resource files
(a mix of CSS/JS/PNG image files) whose combined size is size_mb. Sizes
are weighted randomly rather than split evenly, so a few objects
dominate the page weight like a real page's hero images do, instead of
num_objects equal-sized blobs. Always regenerates so the assets match
the current run's parameters.

Each object's content is a small amount of genuinely valid CSS/JS/PNG —
enough that a real browser (see UE_TRAFFIC_TYPE=webpage's
WEBPAGE_SHOW_BROWSER) actually renders visible boxes and images instead
of blank space / broken-image icons — padded out to the target weighted
size with bytes a parser/decoder ignores (a CSS/JS block comment, or
raw bytes appended after a PNG's IEND chunk, which real PNG decoders
stop reading at). This keeps the original design intent — object
count/size distribution and the resulting request pattern are what
exercise the network path, not the pixels themselves — while also
giving WEBPAGE_SHOW_BROWSER something real to display.

Returns the directory containing index.html.

Write (or overwrite) an OBS profile with the given RTMP push target
and bitrate, with Dynamic Bitrate enabled. DynamicBitrate must live in
the [Output] section, not [SimpleOutput] — a sibling setting under the
wrong section is silently ignored rather than erroring (found by
testing: only moving it to [Output] actually triggered the
"Dynamic bitrate enabled" log line and real bitrate oscillation).

KeyintSec is set explicitly (rather than left at 0/"auto") because OBS
then hands x264 its own default of keyint=250 frames — at FPSCommon=30
that's an 8.3s GOP (confirmed in a live encoder log: "keyint: 250").
A live RTMP viewer can only start decoding from a keyframe, so any
receiver that isn't already mid-connection by the moment OBS's very
first (necessarily-keyframe) frame goes out is stuck waiting for the
*next* one — up to the full GOP length. 1s bounds that worst case
instead of leaving it at whatever x264's default happens to be.

def simple_sns3_test_v14.ffplay_listen_rtmp_cmd (   port,
  window_title,
  duration_s 
) 
Build a shell command that runs ffplay as a one-shot RTMP server:
it accepts a single incoming push connection and plays it live as
frames arrive, no separate ingest/relay process and no local file
involved (verified empirically: ffmpeg/ffplay's rtmp protocol supports
-listen 1, and a pushed stream decodes/plays correctly through it).

RTMP's listen mode serves exactly one connection per invocation and
exits once that connection ends (whether the sender finished normally
or dropped), so this loops for up to duration_s seconds so the window
keeps waiting for a(nother) push instead of just closing after the
first session — e.g. if the sender process gets restarted mid-run.

-fflags nobuffer -flags low_delay trim ffplay's own internal
buffering/decode latency; left at ffplay's default probesize/
analyzeduration rather than shrinking those too, since RTMP already
carries codec params in its onMetaData (so probing is cheap here) and
pushing probesize too low risks ffplay failing to pick up the audio
stream at all.

◆ ffplay_watch_cmd()

def simple_sns3_test_v14.ffplay_watch_cmd (   playlist_url,
  window_title,
  retry_log_path 
) 
Build a shell command that waits for playlist_url to become reachable,
then plays it with ffplay, retrying the whole ffplay invocation if it
fails to actually open the stream.

ffplay exits 0 even when it never managed to play anything (e.g. a
connect timeout, or a 404 partway through a live playlist) — its exit
code alone can't tell success from failure, so this greps ffplay's own
stderr for either of two known-fatal patterns:
  - "<url>: <error>", the line ffmpeg prints whenever avformat_open_input
    fails outright (confirmed empirically for connection-timeout/
    refused/4xx cases opening the *playlist* itself), or
  - "Failed to open segment", printed when a *specific segment* the
    playlist lists 404s (ffplay does not retry or recover from this on
    its own — it just sits there printing "nan" progress forever).
Neither line appears during a genuinely successful playback, so their
absence is what ends the retry loop. Uses FFPLAY_TIMEOUT_US (see its own
comment) as ffplay's own protocol-level connect/IO timeout, which is
otherwise far shorter than what our own scripts tolerate under the same
satellite congestion.

retry_log_path must be unique per concurrently-running ffplay watcher
(e.g. include the UE name/number) to avoid two instances clobbering the
same temp file.

def simple_sns3_test_v14.get_ut_attached_sat_id (   net,
  ut_name 
) 
Return the sat_id (int) the given UT's kernel default route is
currently pointing through, or None if it can't be determined.

This is the same mechanism UtMAC::Handover() uses on the C++ side to
actually switch satellites -- `ip route replace default via
10.0.<sat_id>.2 dev <intf>` (see utMac.cpp's Handover()) -- so reading
the UT's live route back tells us which satellite it's *really*
attached to post-handover, without any new signaling path or C++
change: the route itself is already the ground-truth state the C++
program uses to enforce the handover, just observed from outside
instead of duplicated.

Locked the same way apply_netem() is: this calls node.cmd() on a UT
that other link-control threads (one per satellite) may be calling
concurrently, and Mininet's node shell isn't safe for concurrent use.

◆ setup_tun_tunnel()

def simple_sns3_test_v14.setup_tun_tunnel (   net,
  topo 
) 
Create tun0 virtual NICs and configure policy routing to steer UE
uplink traffic through the SNS3 satellite protocol stack.

WHY tun0 IS NEEDED
SNS3 is a userspace process and has no ability to intercept packets that
the Linux kernel is forwarding.  Without tun0, UE packets would be
forwarded directly by the kernel via the satellite interface, bypassing
the entire SNS3 MAC/PHY scheduling (TBTP, CR, segmentation).
tun0 acts as a pipe between the kernel and SNS3:
- UT side : kernel routes the packet to tun0; SNS3 calls read() to pick
            it up and feed it into the satellite protocol stack.
- NCC side: SNS3 reassembles segments and calls write() to inject the
            reconstructed IP packet back into the kernel, which delivers
            it to the iperf server via normal TCP/UDP demux.

UPLINK PATH  (UE → NCC, through SNS3)
When a UE packet arrives at the UT, the kernel performs IP forwarding
(not TCP processing, since the destination is NCC, not the UT itself).
iptables marks packets from the UE subnet (10.0.200.0/24) destined for
the NCC feeder subnet (10.0.255.0/24) with fwmark=42 in PREROUTING,
before the kernel makes its routing decision.  Policy routing then
redirects marked packets to table 200, which routes them out via tun0
instead of the default satellite interface.
SNS3 AppInterface reads the full IP packet from tun0, segments it into
fixed-size chunks, and transmits each segment in the TBTP-allocated slot
via the satellite socket.  On the NCC side, SNS3 reassembles the segments
and write()s the original IP packet to NCC's tun0; the kernel delivers it
to the iperf server.

WHY PREROUTING, NOT FORWARD
PREROUTING runs before the routing decision, so the fwmark is in place
when policy routing is evaluated.  Marking in FORWARD (post-routing) is
too late: the packet is already committed to the satellite interface.

UT SIGNALING PACKETS ARE NOT AFFECTED
Packets generated by the SNS3 UT process itself (logon, TBTP, CR) enter
the kernel via the OUTPUT chain, which does not pass through PREROUTING.
Therefore fwmark=42 is never applied to them, and they follow the main
table default route directly to the satellite interface.

DOWNLINK PATH  (NCC → UE, bypasses SNS3)
TCP ACKs and all downlink packets follow pure kernel IP forwarding:
NCC → GW → SAT → UT → UE.  netem-emulated delay/loss still applies,
but TBTP scheduling is not involved in the downlink direction.
