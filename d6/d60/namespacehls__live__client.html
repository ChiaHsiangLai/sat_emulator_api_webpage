Detailed Description

hls_live_client.py — simulates a real HLS *live* stream viewer: polls a
growing HLS playlist and downloads new segments as they appear, rather than
assuming the whole segment list is known upfront the way a VOD-style
playlist does. If the network can't keep up with the live encoder's pace,
this client simply falls further and further behind the live edge — exactly
like a real player would — instead of failing or catching up by skipping
ahead.

Each poll of the playlist:
  - discovers any segment names not already downloaded, and fetches them
    (each a separate, independent curl invocation with its own timeout
    budget — a per-segment model, not web_page_client.py's --next-chained
    groups, since here segments arrive one at a time over real time rather
    than all being known at once).
  - if nothing new appeared and the playlist doesn't yet contain
    #EXT-X-ENDLIST, the live encoder just hasn't produced the next segment
    yet — wait POLL_INTERVAL_S and check again.
  - if nothing new appeared and #EXT-X-ENDLIST is present, the live encoder
    has genuinely finished and every known segment has been fetched — done.

Runs until the stream ends or <duration_s> elapses, whichever comes first.
On exit, writes a small key=value summary to <summary_path>.

LIVE LATENCY: each fetched segment's log line reports how far behind the
live edge it was the moment the download finished — i.e. real streaming
latency, not just download time. This is computed from the segment file's
Last-Modified response header (Python's http.server sets this from the
file's actual mtime on NCC's disk, which — since the encoder writes each
segment at its own real playback pace via ffmpeg -re — is effectively "when
this segment was produced"): latency = (time download finished) - (segment's
Last-Modified time). Printed and tracked in real time as segments arrive, so
watching this process's log shows the lag trend live as the run progresses.

usage:
    hls_live_client.py <playlist_url> <duration_s> <summary_path>
    e.g. hls_live_client.py http://10.0.255.254:5101/live.m3u8 300 \\
         log_file/UE_10.0.200.101/video_live_duration.txt

GET seg_url via curl, discarding the body but keeping the response
headers (-D -) to read Last-Modified. Returns (elapsed_s, success,
produced_at_unix_or_None) — produced_at is the segment's Last-Modified
time (Python's http.server sets it from the file's real mtime on NCC's
disk) converted to a Unix timestamp, used to compute live latency in
main(); None if the header was missing/unparseable.

--fail makes curl treat a non-2xx HTTP response as a failure (its exit
code alone doesn't — e.g. a 404 still exits 0 by default). A real stall
(sustained near-zero throughput) or a hard hang past timeout_s also
counts as a failure, same reasoning as web_page_client.py's
fetch_group/fetch_discard.

◆ fetch_text()

def hls_live_client.fetch_text (   url) 
GET url via curl and return the response body as text, or "" if curl
failed OR the body doesn't actually look like an HLS playlist. Before the
live encoder has created the playlist file yet, the server returns a 404
with an HTML error body — that body is non-empty, so without checking
both the exit code and the #EXTM3U marker, it would be misread as a
valid (if oddly formatted) playlist and every line of the error page
would be "discovered" as a bogus segment name.
